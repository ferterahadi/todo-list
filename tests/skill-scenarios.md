# Skill behavior scenarios

Run these with the checkout's skill instructions and separate disposable copies of
`seed/` as `TODO_HUB`. Inspect the resulting files and handoffs as well as the
agent's reply. Use a local Git remote and fixture PR/test results. No scenario needs
to publish a branch, merge a PR, or start a live verification run.

| Skill and request | Fixture | Observable result |
|---|---|---|
| `/todo-execute example-feature parallel tasks 1.1,2.1` | Use the bundled ten-task checklist, register a local repo, and capture feature assignments before implementation. Repeat on a fresh copy with `tasks 99.1`. | Only 1.1 and 2.1 appear in the assignments, including a sequential fallback. The invalid request yields no assignment and leaves hub files, Git refs and worktrees unchanged. |
| `/todo-verify example-feature` | Use a hub-only project in progress. Both ordinary tasks are checked. R11 links to Phase 2 task 2.1 and R12 to Phase 5 task 5.1. Both revisions are tagged `[fixed — awaiting verify]` with open checkboxes. Bind the gate to Phase 5, map 5.1 to `import.spec`, and supply a green run with that spec passing. | Only R12 gets a done tombstone and a checked journal entry with anchor `revision-r12`. R11 keeps its tag, checkbox and detail. The registry stays in progress. The report identifies the missing Phase 2 proof. |
| `/todo-sync example-feature done` | Use a clean, tracked project worktree, zero unshipped commits, one open PR and no verification binding. Repeat with an accepted hub-only project (`repo` is `-`) and one open ordinary task. Neither project has a blocking dependency or revision. | Report the open PR URL. Both registries and the code project's checklist remain byte-identical. The hub-only control ends at 1/1, with status `done` and completion dates recorded. |
| Return a completed review ruling sheet | Give C7 and C8 a confirmed verdict. Mark C7 *fix later* and C8 *fix now*. Exercise both the hub-linked and standalone handoffs and inspect the work sent to the fix loop. | Only C8 reaches `todo-revise` or the standalone implementation brief. C7 stays on the original sheet with its ruling intact and gets no revision, fix assignment, or code change. |
| “Did the rate-limit test pass?” | Seed a completed run with its ID, target and spec verdict. Give the provider separate read and start operations and log all calls. Repeat for a target without a result. | Report the matching run ID, target and spec verdict. The second lookup reports no result. Zero starts or reruns, and all hub files remain byte-identical. |
| Review current work from the hub | Give the linked project worktree a committed doc, a staged file, an unstaged off-by-one defect, and an untracked boundary test. Repeat using an explicit PR and a commit range. | The current-work review sees all four layers and identifies the failing boundary. The PR and range each show only their committed patch. |
| Land two independent reviewed PRs | Both have passing checks. PR A needs owner approval and exits 10; PR B is mergeable. Run the local-remote case in `push-contract.sh`. | Record A's blocker, then check and land B. The resulting base includes B's file and excludes A's. Exit 11 likewise skips that feature; an unexpected or indeterminate outcome stops the queue. |
| Resume an accepted, uncommitted fix | In a cleanly attributed project worktree, edit one file for a revision marked awaiting verification. Leave zero unshipped commits and no PR. Repeat with the revision still open and the edit unfinished. | Name the dirty worktree. For the accepted fix, point to shipping there before verification. For the unfinished revision, point to finishing it there. The digest makes no edits. |
| “Create and plan a self-initiative project called annual-review, no repo” | Start with a clean hub. For a second planning pass, provide only the stored row and plan. | A plan and checklist exist under `projects/self-initiative/annual-review`, with repo `-` and `none — hub-only` recorded. The draft reaches review without asking again for its name, category, repo or permission to plan. A cold replan reuses that scope. Approval is still required before setting `ready`. |
